# Spec: matt-flow v2 (implementation slots + gap-filling waves, ending in PRs)

Status: implemented 2026-11-14.

## Problem
- `matt-flow` was `start -> agent -> end`: no PR (PRs #3, #17 were opened by hand), and `/matt-flow` runs actually went through `quick-task`, so the YAML was unused.
- Few sessions: "max 4" was read as a per-run total, phases did not advance within a run, implementation was disabled by default.

## Design (user decisions, 2026-11-14)
1. **Implementation has its own entry.** `matt-implement-launch.py` checks GitHub: open, `ready-for-agent`, not `in-progress`, all native `blocked_by` closed, no open PR closing it. Oldest first, **2 slots** (`MATT_IMPL_SLOTS`). Each pick gets the `in-progress` label and a new ROOT cezar task (`POST /runs`, workflow `matt-implement`), i.e. a fresh branch off `main`.
2. **`matt-implement`** (one issue): `/implement` (tdd + code-review, Matt's skills) -> `script/agent-ci` (loop x3) -> fresh-eyes `/code-review` with verdicts (loop x2) -> commit -> draft PR -> wait CI (fix loop x2) -> mark ready -> issue comment -> refill slots. Any failure -> issue comment, issue stays `in-progress` = STUCK (never re-picked automatically).
3. **`matt-implement-start`**: entry that only fills the slots.
4. **`matt-flow`**: fills the slots, then the orchestrator (skill `matt-flow`) opens gap-filling sessions in waves (4 in flight, refilled on each report, settled spec -> tickets in the same run), merges them, and the workflow ends with a draft PR (skipped when the branch has no diff).
5. Workflows, skills and scripts in `.ai/cezar/` are versioned (gitignore exception); runtime state stays ignored.

## Out of scope
- Automations (schedule/GitHub poll) to run `matt-implement-start`; can be added later.
- Merging implementation PRs: always the human.
